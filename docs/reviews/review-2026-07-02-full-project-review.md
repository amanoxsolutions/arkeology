# Full project review — concept, features, documentation, and code

## Description

A whole-project review requested by the operator: not only code, but the concept itself, the features, inconsistencies, blind spots, incoherence, technical mistakes, architecture, and assumptions. Conducted at v0.5.0 (commit a6d9b31). Five parallel review passes were run — documentation consistency, core + client layers, MCP tool layer, studio UI + resources, and test suite — plus an analyst-level concept and assumption challenge grounded in the PRD and ADRs. Findings below are deduplicated and cross-corroborated; the two most severe were re-verified directly against the code before inclusion.

## Findings

### Concept & Assumption Challenges

These are not code bugs; they are places where the concept, a claim, or an unexamined assumption deserves a decision. Each includes my recommendation, but the decision is the operator's.

**CA-1 — ✅ RESOLVED (2026-07-02) — The flagship cross-scope topology has no hard security boundary, and the docs imply it does.**
ADR-007 and FR-10 present the tier/visibility gate as a "soft control" with IAM as "the authoritative security boundary." But cross-scope semantic search *requires* all teams to share one S3 Vectors index, and S3 Vectors authorization cannot discriminate inside an index: the condition keys applicable to `QueryVectors`/`GetVectors`/`ListVectors` (`aws:ResourceTag`, `s3vectors:VectorBucketTag` — per the Service Authorization Reference) all evaluate at the index/bucket resource level; none reference per-vector attributes, vector metadata (`tier`, `visibility`, scope), or the request's filter expression. So any participant with `s3vectors:QueryVectors` on the shared index can retrieve **every** team's vectors — no modified server needed, plain CLI/boto3 suffices — including tier-2 titles, descriptions, tags, and embeddings (embedding inversion is a real leak vector). Note the asymmetry: foreign tier-2 *content* in S3 **can** be hard-bounded via prefix-scoped IAM; the shared index cannot. In the shared-index topology, the promise "tier 2 working documents stay strictly project-local" (PRD Vision) is enforced only by the honor system of every participant running an unmodified server. The ADR's escape hatch ("configure IAM for a hard boundary") does not exist for this topology. *Recommendation:* document this as a hard limitation ("cross-scope sharing implies mutual trust at the index level"), and consider per-team vector indexes with tier-3-only replication into a shared index as the future hard-boundary design.

> **Resolution (2026-07-02) — option 1: document the trust model honestly.** ADR-007 revised (corrected Decision text with the content/index asymmetry + Revision section recording the verified IAM condition-key limitation and three hard-boundary candidate designs); `overview.md` scope section corrected; PRD updated in four places (Vision wording, new cross-scope trust constraint under Deployment Prerequisites, FR-10 extended, new Known Limitations entry — all within the "what, never how" rule); README IMPORTANT note sharpened, linking to a new "Cross-Scope Security Model" section in SERVER-REFERENCE (IAM can/cannot table + trust guidance); `cairn://schema/visibility` resource note in `resources.py` corrected (36 resource tests + ruff green). No code-behaviour change. Hard-boundary designs (hosted server / split index) tracked as backlog **B-5**; verified IAM fact recorded in `docs/learnings.md`. Commits `0e21092`, `264350b`.

**CA-2 — ✅ RESOLVED (2026-07-02) — Tier-2 "immutability" is incoherent with silent same-day overwrite.**
FR-13 declares tier-2 content "frozen as a permanent, point-in-time record"; FR-08 says a same type+date+title write "overwrites silently"; `resources.py:116-119` tells agents content "cannot be updated"; `write.py` overwrites any existing key regardless of tier. Combined with slug collisions (C-3 below), a supposedly immutable historical record can be silently destroyed by an unrelated write. Three sources give three different stories. *Recommendation:* decide the real semantic (my suggestion: overwrite allowed but **detected** — warn when the stored title differs from the incoming title) and align FR-13, the schema resource, and the code.

> **Resolution (2026-07-02) — one coherent semantic across code, resource, and PRD.** The C-3 fix settled the semantic once: a write to an existing identifier is **rejected by default** (never silent), and replacement is an explicit, opt-in override. The three sources now agree — `write.py` enforces reject-by-default + explicit overwrite; `resources.py` schema text updated; and the PRD was reconciled (FR-08, FR-13, FR-14, FR-15, FR-26, FR-55, the design-principle bullet, the "Concurrent writes" limitation, and AC-04/AC-05 corrected; AC-64 added for the distinct-title/no-collision guarantee and AC-65 for migration skip-existing — all within the "what, never how" rule; revision date bumped to 2026-07-02). Tier-2 records are immutable in normal use; the explicit override exists only to correct a mistaken write.

**CA-3 — ✅ RESOLVED (2026-07-03) — The PRD sells a deployment topology the code cannot serve.**
PRD Vision/Prerequisites: "Each team may have its own S3 prefix **or bucket** for content storage." `config.py` supports exactly one `ARTIFACT_BUCKET`; `READ_PREFIXES` are prefixes within it. A foreign scope in a different bucket is unreachable by `read_artifact`. *Recommendation:* strike "or bucket" from the PRD, or add bucket-qualified read scopes.

> **Resolution (2026-07-03) — operator-clarified: "or bucket" meant a fully separate deployment, not cross-bucket reads.** The intended semantic of a per-team bucket is a *fully separate deployment* (own content bucket, own vector index, own server) that shares nothing and does not participate in cross-scope search or reads — the topology already permitted by the PRD's Vision ("one bucket per team … is entirely the operator's choice"). The Cross-scope constraint prerequisite (`docs/planning-artifacts/prd.md`) was reconciled to match the code: cross-scope search participants now share **both** the content bucket and the vector index, separated only by prefix (a foreign artifact's full content must be reachable by `read_artifact`, which serves a single content bucket); the "or bucket" option was struck from that context and the separate-deployment / share-nothing case named explicitly. No code change required — the code was already correct; the PRD prose was the sole source of the contradiction. PRD revision date bumped to 2026-07-03.

**CA-4 — ⚙️ PARTIALLY RESOLVED (2026-07-03) — Staleness is named as a fatal risk in the PRD's own Product Value Failure section, yet retrieval has no recency signal.**
"Stale artifacts can confidently point agents in the wrong direction" is listed as an assumption that, if wrong, makes the effort pointless. Ranking is pure cosine similarity; a superseded six-month-old note ranks equal to yesterday's correction. `last_edited_ulid` exists but is unused in ranking; the freshness check covers synthesis artifacts only. *Recommendation:* add optional recency weighting or at least return artifact age prominently so agents can discount.

> **Disposition (2026-07-03) — split into the two options the recommendation names.** **Option A (age transparency, the "at least" floor) — ✅ SHIPPED** as Phase 12 T55 (commit `ef83643`): `search_artifacts` now returns `last_edited_ulid` plus a derived ISO 8601 `last_edited_at` on every result so agents can judge recency and discount stale hits; ranking unchanged. TDD (present/absent/malformed + ordering-invariance), independent review clean, 753 unit tests green, ruff/format/mypy clean; PRD FR-03 + AC-66 reconciled; `resources.py` schema doc updated. Spec: `docs/specs/p12-t55-search-age-transparency.md`. **Option B (recency-weighted ranking) — deferred to backlog B-6** as design-first (ADR before spec): the mechanics are small (single sort site; `last_edited_ulid` already on every vector, no re-index) but the weighting model needs a decision — tier/type-aware decay, [−1,1] cosine-score combination, and default-on vs opt-in. CA-4 stays PARTIALLY RESOLVED until B-6 is decided; Option A has closed the "quietly wrong" transparency gap in the interim.

**CA-5 — `synthesise_artifacts` ceiling of 100 full-content artifacts contradicts the bounded-payload principle.**
NFR-02 exists because full content blows up agent context; FR-19 then allows up to 100 full artifacts in one response (potentially megabytes). Default 10 is sane; the ceiling is not. *Recommendation:* lower the ceiling or add a response-size budget.

**CA-6 — The Product Value Failure and Known Limitations sections are excellent practice** — genuinely self-critical, rare in PRDs. Keep maintaining them; several entries (commit-refs-lost-on-reconcile) are now stale (see D-5).

### Critical

**C-1 — ✅ RESOLVED (2026-07-02) — Production semantic search ranking is broken: `returnDistance` is never requested, so every score is 1.0.**
`clients/vectors.py:137` builds the QueryVectors request with `returnMetadata: True` but no `returnDistance` (AWS default: `false`); line 148 then does `item.get("distance", 0.0)` → `score = 1.0 − 0.0 = 1.0` for every result. Consequences: MCP callers see all-1.0 scores; the "keep highest-scoring section per artifact" logic in `_search_helper.py:157-163` degenerates to first-seen; the final sort is a no-op over ties. **The product's core value proposition — ranked semantic recall — silently does not rank.** The moto extension in `tests/unit/conftest.py` always returns `distance`, masking this in all 711 unit tests; the integration suite asserts nothing about scores. Verified directly. *Fix:* add `"returnDistance": True` to the request; treat a missing `distance` as an error, never as perfect similarity; make the moto extension honour the `returnDistance` flag; add an integration assertion that scores are non-trivially ordered.

> **Resolution (2026-07-02) — request distances + fail-closed on missing distance.** `clients/vectors.py` now sends `returnDistance: True`; a returned vector with no `distance` raises `VectorDistanceMissingError` (`errors.py`) instead of scoring 1.0. The moto `query_vectors` extension (`tests/unit/conftest.py`) now honours the flag — it omits `distance` unless requested — so the simulation is faithful and would catch a regression. Added 3 unit tests (flag sent; missing-distance raises; scores non-trivially ordered) plus a `@pytest.mark.integration` score-ordering assertion. Full unit suite green (741); ruff/format/mypy clean. Spec: `docs/specs/review-2026-07-02-critical-fixes.md`. Commit pending PM commit stage.

**C-2 — ✅ RESOLVED (2026-07-02) — Stored XSS in Cairn Studio with tool-call reach into the reader's scope.**
`static/cairn-studio.html` ~282: `contentArea.innerHTML = marked.parse(content)` with no sanitizer — marked passes raw HTML through. Cross-scope tier-3 `shared` artifacts are readable by design, so a malicious (or compromised) foreign team can store `<img src=x onerror=…>`; the script runs inside the Studio iframe where the ext-apps SDK's `callServerTool` is reachable and can invoke `delete_artifact`, `purge_archived(confirm=true)`, or `write_artifact` **in the reader's scope with the reader's credentials**. Verified directly. *Fix:* `DOMPurify.sanitize(marked.parse(content))` (jsdelivr is already an allowed CSP origin), and set mermaid `securityLevel: "strict"` explicitly.

> **Resolution (2026-07-02) — sanitise before injection + strict mermaid.** `static/cairn-studio.html` now renders `DOMPurify.sanitize(marked.parse(content))` into the reader pane (DOMPurify `3.4.11` pinned from the already-allowed `cdn.jsdelivr.net` CSP origin), and both `mermaid.initialize()` calls set `securityLevel: "strict"`. An audit of every `innerHTML` sink confirmed the reader pane was the only unescaped one — list rows and the metadata pane already route field values through the existing `escHtml()` helper. Verified end-to-end in jsdom with the pinned DOMPurify: `<img onerror>`, `<script>`, `javascript:` href, and `<svg onload>` payloads all neutralised while markdown + a mermaid fence still render. Commit pending PM commit stage.

**C-3 — ✅ RESOLVED (2026-07-02) — Deterministic ID scheme silently destroys artifacts on slug collision.**
`artifact.py:81-113`: (a) any title with no Latin/digit content (CJK, Cyrillic, Arabic, emoji) slugifies to empty and falls back to the constant `"artifact"` — all such tier-3 artifacts of one type share one key, and each write silently destroys the previous one, including its vectors; (b) 60-char truncation collides distinct long titles; (c) punctuation collapse collides "Auth: Module Review" / "Auth module (review)". For a product whose purpose is *never losing persisted memory*, silent overwrite-by-collision is the worst failure mode. ADR-005 documents the normalisation dedup as intentional but did not consider the empty-slug and truncation classes. *Fix:* hash-suffix the fallback slug; on overwrite, compare the stored `title` metadata with the incoming title and warn/reject on mismatch.

> **Resolution (2026-07-02) — operator-approved: hash-suffixed keys + reject-by-default overwrite.** Every artifact ID now carries a deterministic 8-hex SHA-256 suffix of the *full raw title* (`artifact.py` `_title_hash`): tier 2 `{type}-{date}-{slug}-{hash}`, tier 3 `{type}-{slug}-{hash}` — so distinct titles can never collide, structurally eliminating the empty-slug/CJK, truncation, and punctuation-collapse classes. A write whose key already exists is now rejected with `validation_error` unless the caller passes an explicit `overwrite` flag (default `False`), registered over MCP on `write_artifact`/`write_artifacts` (`server.py`). `migrate_artifacts` passes `overwrite=True` (bulk import is designed to re-run — a deliberate split contract). Code-adjacent docs aligned: AGENTS.md ID bullet, ADR-005 revised entry, `resources.py` schema text. 12 unit tests added. **The PRD FR-08/FR-13/CA-2 reconciliation is a separate PM follow-up** — those still describe the old silent-overwrite semantic and no longer match the shipped behaviour. Commit pending PM commit stage.
>
> **Post-fix independent review (2026-07-02) + follow-ups closed.** An adversarial review confirmed the C-3 core mechanism (and C-1/C-2/C-5) clean, and raised two C-3-area items — both now resolved (operator-approved): **(A-1)** `migrate_artifacts` no longer forwards `overwrite=True`; the bulk path now **skips** pre-existing keys and reports them (`skipped_existing`), so re-imports are idempotent and non-destructive and the silent-overwrite class is not reopened on the bulk path; **(A-2)** the collision guard is now **atomic** — `s3.put_object` uses `IfNoneMatch: "*"` (moto-5.2.2-verified), closing the check-then-act TOCTOU race, returning the same `validation_error` on a 412. 8 further unit tests added (749 total green; ruff/format/mypy clean). C-3 is now fully closed.

**C-4 — ✅ RESOLVED (2026-07-02) — The integration test suite destroys real data in the configured deployment scope.**
`tests/integration/test_tools_purge.py:101-260` calls `purge_archived(confirm=True)` against the real `.env` scope, deleting **all** pre-existing archived artifacts plus cascade-deleting syntheses; one test asserts `purged_count >= 2` (acknowledging collateral) and another purges twice to assert 0. Running the documented command `uv run pytest tests/integration/ -q` against a bucket holding real team memory permanently erases the archived set. (Severity context added post-review: the operator's `.env` points at a dedicated test environment by design — the finding is a missing structural guardrail, not active production data loss; shell-var precedence over `.env` still made a real-store run possible.) *Fix:* run purge tests under a dedicated ephemeral `WRITE_PREFIX` (the `unique_run_id` fixture exists but is unused here).

> **Resolution (2026-07-02) — run-scoped prefix isolation.** The suite no longer touches operator-configured scopes at all: `tests/integration/_isolation.py` generates a fresh `integration-tests/<run-id>` / `…-foreign` prefix pair per session (ULID-based, replacing the unused `unique_run_id` fixture), and a new autouse `isolate_run_scope` fixture in `tests/integration/conftest.py` overwrites `WRITE_PREFIX`/`READ_PREFIXES` in `os.environ` right after `.env` loads — `.env` remains only the credentials/resource source. Session-end teardown best-effort deletes every S3 object and vector under both prefixes (scope-filtered, chunked). The `purged_count >= 2` tolerance is now exact (`== 2`). 9 new unit tests exercise the teardown against moto; full unit suite green (721), ruff/mypy clean; the isolated integration suite ran end-to-end against the test environment with zero leftover `integration-tests/` objects or vectors. CONTRIBUTING.md gained an "Integration tests" section; README links to it.

**C-5 — ✅ RESOLVED (2026-07-02) — Cross-scope gate bypass in `check_synthesis_freshness` (non-negotiable rule violation).**
`tools/freshness.py:127-140` looks up source artifacts by bare `{"artifact_id": {"$eq": source_id}}` — no scope clause, no tier/visibility gate. It is the only read path in the codebase touching foreign vectors ungated: it reads and reports the `date`/`status` of foreign tier-2 or hidden artifacts (existence, archival state, update recency) that `read_artifact` would deny. AGENTS.md lists "never bypass the cross-scope gate" as non-negotiable. *Fix:* apply the same gate as `list.py:142-150` to non-own-scope source IDs; classify gated-out sources as inaccessible.

> **Resolution (2026-07-02) — apply the list.py cross-scope gate.** `tools/freshness.py` Step 6 now gates every source-metadata lookup exactly as `list.py` does: own-scope (`startswith(scope + "/")`) always readable; a foreign source readable only when tier 3 ∧ `visibility="shared"`; otherwise classified inaccessible (`None`) so it surfaces as *missing* and its `date`/`status` are never read or reported — no leak of whether a foreign artifact exists. 2 unit tests added (foreign tier-2 source not leaked; foreign tier-3 shared read normally). Closes the non-negotiable-rule violation. Commit pending PM commit stage.
