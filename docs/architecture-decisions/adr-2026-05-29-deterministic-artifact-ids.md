# Deterministic Slug-Based Artifact Identifiers

## Description

Every artifact stored by cairn-mcp has a unique identifier used as its S3 object key and as
the primary lookup key in the vector index. This decision records the choice to generate that
identifier deterministically from the artifact's own attributes, with no random component.

## Status

Accepted

## Context

Artifact identifiers serve three purposes simultaneously:

1. **S3 object key** — must be a valid, stable, human-readable string so artifacts are
   browsable in the S3 console without a separate manifest.
2. **Idempotency key** — writing the same logical artifact twice must produce exactly one
   stored artifact with no duplicates (NFR-06). The ID must be the same across retries.
3. **Deduplication signal** — tier 3 artifacts are living documents; the same plan or ADR
   updated over time must always map to the same ID so the second write overwrites the first
   (FR-08, FR-15).

The key design constraint is that tier 2 and tier 3 artifacts have different update semantics:

- **Tier 2** (session-scoped, immutable after write): a code review written on Monday and
  another on Tuesday are two distinct artifacts. The date participates in the ID.
- **Tier 3** (permanent, updated in place): a plan updated on Monday and again on Tuesday is
  one artifact. The date must not participate in the ID.

UUID v4 was considered and rejected: it is not idempotent (each call generates a new ID),
not human-readable, and offers no deduplication signal. A content hash was also rejected: it
changes with every content edit, making in-place updates impossible without an external
lookup table.

## Decision

Artifact IDs are generated by `generate_artifact_id()` in `artifact.py` using the following
schemes:

- **Tier 2**: `{type_slug}-{date}-{title_slug}` — e.g. `code-review-2026-05-30-auth-module`
- **Tier 3**: `{type_slug}-{title_slug}` — e.g. `adr-use-s3-vectors-as-semantic-index`

Both `type_slug` and `title_slug` are produced by the same normalisation pipeline:
transliterate Unicode → ASCII (NFKD), lowercase, replace runs of non-alphanumeric characters
with a single `-`, strip leading/trailing `-`, truncate to 60 characters, re-strip trailing
`-` after truncation. An empty result after all steps falls back to `"artifact"`.

The full S3 key is `{WRITE_PREFIX}/{artifact_id}{file_extension}` where `file_extension` defaults to `.md` (e.g.
`team/project/code-review-2026-05-30-auth-module.md`). Section vector keys extend this with a
section slug: `{s3_key}#{section_slug}` (e.g. `team/project/code-review-2026-05-30-auth-module.md#overview`).

## Alternatives Considered

| Option | Pros | Cons |
|--------|------|------|
| **Chosen** — slug from type + date + title (tier 2) / type + title (tier 3) | Deterministic; idempotent; human-readable in S3 console; deduplication semantics match tier update rules | Two different titles that slugify to the same string are treated as the same artifact — intentional but requires documentation |
| UUID v4 | Globally unique; no collision risk | Not idempotent across retries; not human-readable; offers no deduplication — requires a separate lookup index for idempotency |
| SHA-256 content hash | Unique per content; changes detect modifications | Hash changes with every content edit — makes in-place tier 3 updates impossible without a separate key registry; not human-readable |
| Sequential integer | Simple; predictable | Requires a counter with concurrent-write safety; not deterministic from attributes; not human-readable |

## Consequences

- The same artifact type + date + title combination written multiple times on the same day
  (tier 2) always produces one stored object and one set of index entries — idempotent (NFR-06).
- A tier 3 artifact (same type + title) always overwrites in place, regardless of how many
  days apart the writes are (FR-15). The write path for tier 3 must also clean up orphaned
  section vectors from the previous version — handled by querying the index for all vectors
  with `artifact_id` matching the new ID and deleting any whose section slug is no longer
  present.
- Two titles that normalise to the same slug (e.g. `"Auth Module"` and `"auth_module"`) are
  treated as the same artifact. This is intentional deduplication, not a collision — document
  this clearly to operators.
- S3 keys are fully human-readable and browsable in the AWS console without a manifest file.
- The `#` character used as the section vector key separator is confirmed valid by AWS
  documentation and empirically by the T17 integration test suite (2026-05-31).
