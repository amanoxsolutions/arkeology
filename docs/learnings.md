## Learnings

- **S3 Vectors boto3 service client name**: `"s3vectors"` (confirmed from botocore service catalogue during Phase 1 T3 implementation)
- **S3 Vectors `GetIndex` output**: returns `{"index": {"dimension": N, ...}}`; dimension field is nested under `index` key, not at root level
- **S3 Vectors `QueryVectors` response**: uses `distance` field (not `score`); for cosine, lower distance = more similar. Converted to `score` via negation in `VectorsClientImpl.query_vectors()`
- **S3 Vectors `list_vectors_by_metadata`**: `ListVectors` API has no server-side metadata filter parameter; implemented as paginated scan + client-side filter. Performance acceptable for Phase 1; consider optimizing in later phases if needed
- **Bedrock Titan Text Embeddings v2 request shape**: `{"inputText": text}` — `dimensions` parameter is optional; response shape: `{"embedding": [...], "inputTextTokenCount": N}`
- **pydantic-settings + mypy strict**: requires `plugins = ["pydantic.mypy"]` in `[tool.mypy]` to avoid spurious "missing required arguments" errors on `Settings()` calls
- **`#` character in S3 Vectors keys**: valid by AWS documentation — key type is `String` with length constraint 1–1024 and **no character pattern restriction**; the official getting-started tutorial uses spaces in keys ("Star Wars", "Jurassic Park"), which is more permissive than `#`; empirical confirmation planned in T17
- **`WRITE_PREFIX` must be non-empty**: empty prefix causes `startswith("")` to always return True, silently bypassing the cross-scope access control gate; default changed to `"artifacts"` and a validator now rejects empty/whitespace values at startup
- **Slug-based artifact IDs over hash-based**: collisions are intentional deduplication; human-readable in S3 console; two titles normalising to the same slug represent the same artifact (idempotency contract)
- **`$or`, `$in`, and `$nin` in S3 Vectors filters**: all confirmed supported by AWS documentation ([Metadata filtering](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-vectors-metadata-filtering.html)); `$nin` explicitly listed as "Match none of the values in array" with "Non-empty array of primitives" constraint — non-empty array required (omit the clause on first iteration); `$or` and `$in` enable a single combined query per search iteration rather than one per scope
- **S3 Vectors index configuration is immutable**: dimension, distance metric, index name, and non-filterable metadata keys cannot be changed after index creation — confirmed by AWS documentation ([Vector indexes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-vectors-indexes.html)); a mismatch between the configured embedding model output dimension and the index dimension requires the admin to create a new index; document this as an explicit warning in T19 setup docs
- **S3 Vectors `PutVector` upsert — CONFIRMED empirically (T17, 2026-05-31)**: integration test suite ran 44 tests against live AWS credentials; tier 3 re-write integration tests passed green with zero duplicate vectors; `PutVectors` silently overwrites an existing key — no code change required; Q1 closed as confirmed.
- **`#` character in S3 Vectors keys — CONFIRMED empirically (T17, 2026-05-31)**: write and search integration tests exercised section-vector keys of the form `{artifact_id}#{section_slug}` without any key-format error from the S3 Vectors API; `#` is a valid key character in production.
- **S3 Vectors `$nin` operator — CONFIRMED empirically (T17, 2026-05-31)**: search integration tests exercised the `$nin` filter in re-fetch loop iterations; no filter-validation errors returned from S3 Vectors; the operator works correctly with a non-empty array constraint.
- **T17 integration suite baseline**: 44 tests, 0 failures, runtime ≈ 94 s against live AWS (eu-west-1); all tools covered (write, search, read, list, archive, delete, purge, health, synthesise, client layer).
- **tags vector metadata storage**: stored as `list[str]` in vector metadata (not comma-joined string) so that `{"tags": {"$eq": "tag"}}` filter works correctly; S3 object metadata stores as comma-joined string (S3 only supports string metadata values)
- **Phase 3 top-level exception handler pattern**: all tool public functions delegate to `_<name>_inner` and wrap the await in `try/except Exception` returning `{"error": "internal_error", "message": str(exc)}` — this prevents any unexpected exception from escaping as a raw Python exception to the MCP caller; follow this pattern for Phase 4+

- **L1+L2 superseded by Z1 (2026-06-03)**: Post-implementation review revealed two structural problems with the L1+L2 approach. (1) L1 assumed sub-agents spawned via the `task` tool receive independent Arkeology MCP connections — empirical evidence (persistent performance problems) indicates sub-agents share the parent's stdio pipe, serializing all write_artifact calls and collapsing write parallelism to zero. (2) migrate.py duplicated the write path and was never updated with P1's concurrent section embedding — the script's write_artifact() still uses the old sequential for-loop, making it 2× slower per artifact than calling the MCP server with P1. Both problems trace to the same root cause: bypassing MCP required duplicating write logic, and duplicated code does not inherit fixes. Z1 (write_artifacts + migrate_artifacts MCP tools) resolves all three problems: moves all document-level and section-level parallelism inside a single MCP call; eliminates the transport bottleneck; eliminates duplication by moving description generation server-side into migrate_artifacts. migrate.py is deleted entirely — the skill ships SKILL.md + schema only, with no bundled scripts, and is fully cross-IDE compatible (OpenCode, Claude Code, Codex, Copilot). See brainstorming-write-performance-2026-06-01.md Sessions 2026-06-03 Part 1 and Part 2 for full analysis.

- **T31 — opencode project config filename is `opencode.json` (no dot prefix)**: `opencode.json` at the workspace root is the officially documented project-level config. `.opencode.json` (dot-prefixed) is NOT reliably picked up — it was silently ignored in a real installation test where the startup log showed only the three global config files loading and never the project file. Do not create `.opencode.json`; create `opencode.json`. The dot-prefix variant may be detected if already present from an earlier mistaken setup but must never be written by the setting-up-arkeology skill.

- **T31 — opencode MCP config merge is additive at the server-name level**: A project-level `opencode.json` that introduces a server name not present in the global config adds it to the merged set without disturbing existing global servers. Confirmed empirically: a project config containing only `arkeology` merged with a global config containing `mcp_aws`, `mcp_iac`, and `mcp_awscw` — all four servers were active in the session.

- **T31 — opencode must be started from the project directory to load project config**: opencode only reads a project-level `opencode.json` when started from the directory that contains it (or a subdirectory that traverses up to find it). Starting from any other directory silently skips the project config — only global configs load, with no error or warning. Skills that configure project-level MCP entries must explicitly tell the operator to restart the MCP client from the project directory.

- **T31 — Copilot CLI supports per-project `.mcp.json` since v0.0.401**: GitHub Copilot CLI added workspace-level `.mcp.json` support in v0.0.401 (≈ February 2026). The official docs page was not updated at time of discovery — the feature was found via GitHub issue comments. `.mcp.json` at the workspace root is shared between Claude Code and Copilot CLI; both use the `mcpServers` top-level key. `servers` (VS Code Copilot Chat's key) is NOT recognised by Copilot CLI. Copilot CLI also reads `~/.copilot/mcp-config.json` as a merge layer — this is a client behaviour, not something the setting-up-arkeology skill writes.

- **T31 — MCP skill agents default to global config paths when not explicitly anchored**: Without an instruction that specifies the exact file path derived from the current working directory, an agent configuring an MCP client will default to the globally-known config path it learned during training (e.g., `~/.config/opencode/opencode.json` instead of the project-local `opencode.json`). Installing skills must resolve and name the absolute target path — including a concrete example such as `/home/alice/myproject/opencode.json` — before the agent touches any file. A reference table alone is insufficient.

- **T31 — opencode uses `environment` (not `env`) and array `command`**: opencode's MCP server config uses `environment` as the env-vars key and requires `command` as a JSON array (e.g. `["uv", "run", ...]`). Every other supported MCP client (Claude Code, Copilot CLI, Codex) uses `env`. VS Code + Copilot Chat additionally uses `servers` as the top-level key instead of `mcpServers`. These differences must be prominently flagged in any skill that generates MCP config entries.

- **T33 — Plugin distribution: known implementation gotchas (derived from post-delivery fixes to the reference implementation; record here before speccing T33)**:

  - **`git+ssh://` URL format**: the correct npm git+ssh format uses a forward slash after the hostname: `git+ssh://git@github.com/org/repo.git`. The SCP-like colon form (`git+ssh://git@github.com:org/repo.git`) is valid for bare git but is an **invalid URL in Node.js** — it throws `ERR_INVALID_URL`. The OpenCode plugin silently never installs with the colon form: no entry in `~/.config/opencode/node_modules/`, config hook never fires, no skills appear.

  - **YAML description quoting for `gh skill install`**: any SKILL.md whose `description` frontmatter value contains the two-character sequence `: ` (colon-space) **must** be wrapped in double quotes. Python's `yaml.safe_load` is lenient and parses plain scalars with `: ` without complaint. The Go YAML parser used by `gh skill install` is strict and rejects them. This caused silent failures for affected skills. Solution: pre-validate all SKILL.md files at commit time with a `scripts/validate.py` check (or equivalent) that flags unquoted descriptions containing `: `.

  - **`gh skill install` required flags — all four are mandatory**:
    - `--from-local`: installs from the local clone, not via 32+ remote GitHub API calls; works offline; uses exactly the cloned version.
    - `--agent github-copilot`: without this, the command prompts interactively for agent selection and hangs in a terminal script.
    - `--scope user`: installs to `~` (user-level); without it, scope defaults vary and skills may not be globally available.
    - `--force`: overwrites on re-run without prompting; required for idempotency.

  - **Copilot detection signal**: use `command -v copilot` (not `command -v gh`) in `install.sh` to detect GitHub Copilot. `gh` is GitHub's general-purpose CLI used by all developers for PRs, issues, and releases — its presence on PATH says nothing about which AI coding tool is installed. `gh` and `gh skill` are then checked as internal prerequisites inside the Copilot section, not in the top-level detection block.

  - **`marketplace.json` required fields**: the minimal valid `marketplace.json` for Claude Code requires `$schema`, `name`, `owner: {name: ...}`, and `plugins[].source` using a relative path (`"./plugins/arkeology"`). A bare `path` field (without the `source` key) is not valid. Missing `owner` or `$schema` causes the marketplace registration to fail silently.

  - **`plugin.json` must omit `version`**: including a static `version` field in `plugins/arkeology/.claude-plugin/plugin.json` pins the plugin to that version string and prevents users from receiving updates via `claude plugin update`. Omitting `version` causes Claude Code to use the commit SHA, treating every push as a new version automatically.

  - **OpenCode session-refresh message**: print both SSH and HTTPS plugin lines verbatim in the final summary section of `install.sh` — not only earlier in the OpenCode section where they scroll off before the engineer reaches the bottom. Engineers need the plugin line where they are ready to act on it.

- **T33 — `marketplace.json` has two distinct `name` fields (post-delivery fix, 2026-06-10)**: `claude plugin install arkeology@arkeology` resolves as follows — `arkeology` is the marketplace identifier (top-level `"name"` in `marketplace.json`); `arkeology` is the plugin lookup key (the `"name"` field inside the `plugins[0]` entry). Claude Code searches the `plugins` array for an entry whose `name` matches the install-command prefix. Setting `plugins[0].name` to `"arkeology"` (the marketplace name) instead of `"arkeology"` causes "Plugin 'Arkeology' not found in marketplace 'Arkeology'" at install time — the two keys are structurally identical in the JSON but serve completely different lookup roles.

- **T33 — `marketplace.json` `$schema` must be the Anthropic URL (post-delivery fix, 2026-06-10)**: the `$schema` field must be exactly `"https://anthropic.com/claude-code/marketplace.schema.json"`. Claude Code uses this URL to select its source-type parser; any other value (e.g. `"https://claude.ai/schemas/plugin-marketplace.json"`) causes "This plugin uses a source type your Claude Code version does not support" at install time, even on a current Claude Code version. Additionally, `plugins[0].author` must be an object (`{"name": "…"}`), not a plain string — use the amanox-ai-agents `marketplace.json` as the canonical reference for field shapes.

- **T33 — OpenCode plugin hook API: named hook inside returned object, not direct function (post-delivery fix, 2026-06-10)**: the correct OpenCode plugin export shape is `export default function(context) { return { config: (cfg) => { /* mutate cfg */ } } }`. The outer function receives the OpenCode context `{ project, client, $, directory, worktree }`, not the config. Returning a named `config` hook inside the object is required — exporting a function that takes and returns `config` directly causes the mutation to land on the context object instead of the config; the `try/catch` swallows the error silently and no skills are registered. Always use the `amanox-ai-agents` `.opencode/plugins/amanox.js` as the canonical reference for the correct hook shape.

- **T33 — OpenCode never auto-updates git plugin caches (post-delivery fix, 2026-06-10)**: OpenCode fetches git plugins into `~/.cache/opencode/packages/<name>@git+<url>` on first install and does not re-fetch on subsequent restarts. To get a newer version (bug fix or new content), the cache directory must be deleted explicitly — OpenCode then re-clones on next startup. `install.sh` now does `rm -rf ~/.cache/opencode/packages/arkeology@git+*` in the OpenCode section so every run of the script forces a fresh fetch. The glob `arkeology@git+*` covers both the SSH and HTTPS URL variants.

- **S3 Vectors per-request limits (verified 2026-06-25)**: PutVectors **500**, DeleteVectors **500**, GetVectors **100**, ListVectors `maxResults` **1000** per call ([S3 Vectors limits](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-vectors-limitations.html)). Any vector-client method that accepts a key/vector list must chunk to its cap — do the chunking **inside** the client method (`VectorsClientImpl.get_vectors`/`delete_vectors`/`put_vectors_batch`) so every call site is automatically safe, rather than at individual callers (`delete_artifact`, `purge_archived`, and `list_artifacts` had all called `get_vectors` on full own-scope key sets and would `ValidationException` past 100 keys). Gotcha: **moto does not enforce these caps**, so an unbatched over-limit call passes silently against moto — verify chunking in unit tests by `mocker.spy(client._client, "get_vectors")` and asserting the chunk count and that every call's `keys` length ≤ the cap.

- **FastMCP/MCP template resources cannot carry per-read annotations (verified 2026-06-25, FastMCP 3.4.2)**: a resource **template** (e.g. `arkeology://artifact/{id}`) declares its `annotations` once at registration — they are static and cannot vary per `{id}`. The only per-read channel, `mcp.types.TextResourceContents`, exposes `uri`/`mimeType`/`meta`/`text` and has **no `annotations` field**. Therefore a per-id/per-read annotation such as `lastModified` is **not expressible** for a template resource in this stack; only static, identical-for-every-read annotations like `audience` can be emitted. Verified against the installed `TextResourceContents` model fields and `fastmcp/resources/base.py` (annotations live on the resource/template definition, not on read contents). Consequence: T42's per-read `lastModified` requirement is waived; the ULID→ISO helper (`_artifact_last_modified`) is retained and unit-tested in isolation, ready to wire in if/when the protocol gains per-read content annotations. Do not spec per-id resource annotations on a template until then.

- **`StrEnum` (not plain `Enum`) for any value crossing the MCP boundary or stored in AWS metadata (2026-06-29)**: when centralising scattered string literals (error codes, artifact statuses) into an enum, the member must be `enum.StrEnum`, not plain `enum.Enum`. A plain `Enum` member serializes via `json.dumps` as `"ErrorCode.CREDENTIAL_ERROR"` and stores into S3/vector metadata as that qualified name — silently changing the wire value and breaking callers and `$eq` filters. `StrEnum` *is* a `str`: it JSON-serializes to the bare value (`"credential_error"`), compares equal to its literal (`ErrorCode.CREDENTIAL_ERROR == "credential_error"`), and is set-membership/`$eq`-filter compatible. Verify with `json.dumps({"e": ErrorCode.CREDENTIAL_ERROR}) == '{"e": "credential_error"}'` before relying on it. Any future enum whose value is returned to an MCP caller or written to S3/vector metadata must be a `StrEnum`. Introduced in `src/arkeology/constants.py` (`ErrorCode`, `ArtifactStatus`).

- **S3 Vectors IAM cannot discriminate within an index (confirmed 2026-07-02, [Service Authorization Reference](https://docs.aws.amazon.com/service-authorization/latest/reference/list_amazons3vectors.html))**: the only condition keys applicable to `QueryVectors`/`GetVectors`/`ListVectors` are `aws:ResourceTag/${TagKey}` and `s3vectors:VectorBucketTag/${TagKey}` — both evaluate against tags on the index/bucket *resource*, so they can separate access between indexes (ABAC) but evaluate identically for every caller of one shared index. No condition key references vector keys, vector metadata, or the request's filter expression; vector-bucket resource policies use the same actions/resources/keys. Consequence: in any shared-index topology, the tier/visibility gate is enforceable only by the querying process itself — a hard cross-team boundary requires separate indexes (per-team index + replicated shared index), not IAM conditions. Foreign tier-2 S3 *content* can still be hard-bounded via prefix-scoped IAM; the index cannot.

- **Slug fallback and truncation collisions are data loss, not deduplication (discovered 2026-07-02)**: the intentional-dedup contract ("two titles normalising to the same slug are the same artifact") holds only for titles that survive transliteration. Titles with no Latin/digit content slugify to empty and fall back to the constant `"artifact"`, collapsing every such artifact of one type (tier 3) or type+date (tier 2) onto one key — each write silently destroys the previous artifact and its vectors. The 60-char truncation collides distinct titles sharing their first 60 slug characters. Any change to the ID scheme must treat these two classes separately from intentional dedup: hash-suffix the empty-slug fallback, and detect overwrites by comparing stored `title` metadata against the incoming title.

- **S3 Vectors `QueryVectors` omits `distance` unless `returnDistance: true` is requested (discovered 2026-07-02)**: the request flag defaults to `false` in the botocore service model, so a request that sets only `returnMetadata` receives results with **no** `distance` field. `VectorsClientImpl.query_vectors` compensated with `item.get("distance", 0.0)`, which converts "field not requested" into `score = 1.0` (perfect similarity) for every result — production search ranking silently degenerates while all unit tests pass, because the moto `query_vectors` extension always returns `distance` regardless of request flags. Rules: (1) always set `"returnDistance": True` explicitly; (2) treat a missing `distance` as an error, never default it to a valid score; (3) test doubles for `query_vectors` must honour the `returnDistance`/`returnMetadata` request flags rather than always returning both fields, or this class of divergence is invisible to the unit suite; (4) integration tests must assert scores are non-trivially ordered, not just present.

- **S3 object annotations are unsupported by moto but present in boto3 (verified 2026-07-02, cross-referencing brainstorm)**: the S3 annotation APIs (`PutObjectAnnotation`, `GetObjectAnnotation`, `ListObjectAnnotations`, `DeleteObjectAnnotation`) are all present in the installed `botocore` 1.43.36 service model, but `moto` 5.2.2 has **zero** request handling for them (confirmed by inspecting `moto.s3.responses`/`moto.s3.models` — no annotation routing). Because the project mandates moto for all S3 unit tests, any code path that reads or writes annotations must be exercised through a self-authored `conftest` moto extension, exactly like the existing `query_vectors` cosine-similarity patch — plain `@mock_aws` will silently no-op the annotation calls. Relevant to the planned annotation-backed storage of `commit_refs`/`references` (see `brainstorming-2026-07-01-artifact-cross-referencing.md`, D12). **AWS CLI support is version-gated**: annotation operations are absent in aws-cli 2.34.44 (`aws s3api put-object-annotation` → "invalid choice") but present from 2.35.14 (all four ops). A CLI-native setup/onboarding probe must therefore guard on a minimum aws-cli version, or fall back to a boto3 snippet via `uv run`. The IAM actions a deployment must grant for annotation storage are `s3:PutObjectAnnotation`, `s3:GetObjectAnnotation`, `s3:ListObjectAnnotations`, and `s3:DeleteObjectAnnotation` (confirmed from the CLI operation help). Annotations are also region/bucket-type gated (unavailable in UAE/Bahrain regions and on directory buckets — the bucket type the S3 Express One Zone storage class uses, so one category rather than two — and on Outposts buckets) and are **wiped when the object is overwritten** by `PutObject`.

- **Session-scoped `autouse` fixtures are the only reliable way to influence `Settings()` construction in the integration suite (confirmed 2026-07-02, integration-suite isolation work)**: a session-scoped `autouse=True` conftest fixture executes before any explicitly-requested session-scoped fixture, even without a declared dependency — this ordering guarantee is what lets `load_env` and the new `isolate_run_scope` fixture finalise `os.environ` (`.env` load, then run-scoped `WRITE_PREFIX`/`READ_PREFIXES` override) before any test file's own `settings()` fixture builds a `Settings()` object. Any future fixture that must affect `Settings` construction in `tests/integration/` must follow the same pattern: session scope + `autouse=True` + an explicit dependency on `load_env` to pin relative order — module- or function-scoped setup runs too late.

- **`monkeypatch` does not revert direct `os.environ` mutations (discovered 2026-07-02, integration-suite isolation work)**: `monkeypatch.setenv`/`delenv` auto-revert only the changes monkeypatch itself performed. A function under test that assigns `os.environ[...] = ...` directly leaks that state past the end of a test that merely wraps the call in `monkeypatch` — in this project it leaked `READ_PREFIXES` session-wide and broke `test_check3_skipped_when_no_read_prefixes` in a different file. Safe patterns for testing env-mutating code: (1) dependency-inject the target mapping (`env: MutableMapping[str, str] | None = None`, defaulting to `os.environ`) and pass a plain `dict` in tests — the pattern now used by `apply_run_scope_env`; or (2) snapshot and restore the affected keys in a manual `try/finally`. Test-order-dependent failures in unrelated files are the telltale symptom.

- **T39 — Spying on `asyncio.Semaphore` constructor value with `mocker.patch(..., wraps=...)` (2026-06-11)**: Use `mocker.patch("arkeology.tools.<module>.asyncio.Semaphore", wraps=asyncio.Semaphore)` to record what value is passed to the semaphore constructor while still creating a real, functional semaphore — `async with semaphore:` works normally and no `RuntimeError` is raised. Without `wraps=`, the mock returns a `MagicMock` and `async with` fails immediately. Pitfall: choose a probe value that cannot be confused with other semaphores created in the same code path (e.g. `section_concurrency` defaults to 5 in `write.py` — an `artifact_concurrency=5` spy assertion passes even if the artifact semaphore was never set to 5, because the section semaphores satisfy it). Always use a probe value outside the range of any other concurrency setting in the call path.

- **Recency-based ranking needs no re-index — unlike an embedding-model/dimension change (2026-07-03, T54 search age-transparency work)**: the high-friction "changing `BEDROCK_EMBEDDING_DIMENSIONS`/model requires a full re-index" rule does **not** extend to adding a temporal/recency signal to search. `last_edited_ulid` is already written into every vector's metadata (`write.py`) and returned on every query, and result ranking is applied in-process *after* the vector query in `_search_helper.py:run_search_loop` (the single sort site, shared by `search` and `synthesise`). Consequences for future recency-ranking work (backlog B-6): the temporal signal is already present with zero migration; the ranking change is localized to one sort; and test doubles need no change because recency is applied post-query (the moto `query_vectors` extension is untouched). The genuine design work is the weighting model — tier/type-aware decay, combining a decay factor with cosine scores that live in [−1, 1], and default-on vs opt-in — not data plumbing. T54 shipped the transparency half (surface `last_edited_ulid` + derived `last_edited_at` on each search result, no ranking change); the ranking half is B-6.

- **S3 Vectors reverse-lookups must branch on the index's non-filterable-key declaration (2026-07-03, Phase 12 / T50)**: a `$eq` (or any filter) on a metadata key declared **non-filterable** at index creation fails with `ValidationException` — filtering works only on filterable keys. Non-filterable keys are still stored and returned in query results; they just cannot appear in a `filter_expr`. Consequence for reverse-lookups ("which artifacts reference X?"): a field that must be non-filterable because it is large or optional (e.g. `source_artifacts` — up to ~100 ids, over the 2 KB filterable budget) cannot be resolved with a server-side `$eq`; narrow instead with a *filterable* prefilter that bounds the candidate set (for `source_artifacts`: `type = synthesis`, since only syntheses carry it) and do the membership check in-process. A small, non-narrowable reference field (`references`) is better kept *filterable* so both its reverse-lookup and its `list_artifacts` filter stay server-side. General rule: classify each metadata field by (used in `$eq`/range filters?) and (size), keep the classification in one constant (`NON_FILTERABLE_METADATA_KEYS`) that MUST equal the index's declared slots — and remember that declaration is **immutable at index creation**, so changing it requires deleting and recreating the index (losing all vectors), exactly like the dimension.

- **Testing `reconcile_index`'s re-index path against an already-indexed artifact requires the failure-log-replay route, not the orphan scan (2026-07-04, Phase 12)**: `_reconcile_index_inner`'s orphan scan explicitly filters out any own key already present in `indexed_artifact_ids`, so an already-indexed artifact can *never* surface as an orphan. To exercise re-index against pre-existing vector state — needed to test the union-of-both-stores restore (an orphan-scan artifact has no pre-existing vector to union against) — seed a failure-log entry and drive the replay path, which re-indexes unconditionally by `artifact_id`. Any future reconcile edge-case test involving pre-existing vector metadata must use this route.

- **An MCP resource whose `{id}` can contain slashes needs FastMCP's wildcard-path param `{id*}` — not `{id}` or `{+id}` (2026-07-04, Phase 12)**: Arkeology's operative `artifact_id` is the full S3 key `{write_prefix}/{id}{ext}`, which contains slashes. FastMCP 3.4.2 (`fastmcp/resources/template.py` `build_regex`) compiles a plain `{id}` template param to `(?P<id>[^/]+)` — a single path segment — so a full-key `arkeology://artifact/{id}` read silently fails with `NotFoundError` on any real id. RFC-6570 reserved expansion `{+id}` is **not** the fix: the vendored low-level `mcp` SDK mis-parses `+id` into an invalid regex group name. The correct form is FastMCP's wildcard-path parameter `{id*}`, which compiles to `(?P<id>.+)`; the Python handler parameter stays `id` (the `*` is stripped when the param name is extracted). Test resolution through the *registered* template (`app.read_resource(...)`), not just the inner content helper — otherwise the template-regex bug hides behind a passing helper test.

- **S3 Vectors server-side filter semantics — CONFIRMED empirically (2026-07-06)**: two `query_vectors` behaviours were verified by driving the real API directly (not through `matches_filter`). (1) **`$gte`/range operators are Number-only server-side** — a String/ULID `$gte` is rejected with `ValidationException: Invalid filter`. So ULID-range filtering (e.g. `propose_commit_links`' `since_ulid` cursor via `list_vectors_by_metadata`) must stay **client-side** and must never be pushed into a server-side `filter_expr`; `matches_filter`'s permissive string `$gte` is safe only because no server-side caller relies on it. (2) A **~4 KB `$nin` filter expression is accepted** — no distinct QueryVectors filter-expression size cap was observed at that size beyond the documented 2 KB *per-vector filterable-metadata* limit, so the `_NIN_EXCLUSION_BYTE_BUDGET` guard is defensive, not strictly required at that scale. Both facts are pinned by `tests/integration/clients/test_vectors_filter_semantics.py`, which now backs the fidelity of the unit-suite moto `query_vectors` extension.

- **Offload a whole synchronous helper with one `asyncio.to_thread`, not by making the client Protocol async (2026-07-05, event-loop offload work)**: `reconcile_index`'s `_reindex_artifact` is a sync helper containing several buried blocking calls (multiple `bedrock.embed`, `put_vector`, and Bedrock's retry `time.sleep`). Wrapping the *entire* helper in a single `asyncio.to_thread(...)` at each call site keeps all of it off the event loop without making `BedrockClientInterface.embed`/`invoke_text_model` async — which would ripple through the `typing.Protocol` interface, every concrete + fake implementation, and every synchronous caller (`startup.py`, `health.py`). Prefer this whole-helper offload for future async work in this codebase; it is also the basis for the still-open `health.py` blocking-Bedrock probe fix (tracked as a known gap in a `bedrock.py` comment). The write path's per-artifact executor offload (`_EMBED_EXECUTOR`) remains the pattern for the bounded-concurrency embedding fan-out.

- **Pydantic's default (lax) coercion silently converts a wrong-typed value before any `field_validator` runs — use `Field(strict=True)` where the type itself is the contract (2026-07-06)**: `Artifact.tier: int` accepted a numeric string like `"2"` because pydantic's default lax mode coerces `"2"` → `2` during model construction, *before* `_require_valid_tier`'s `field_validator` ever runs — so a caller's type mistake (string instead of int) passed model construction undetected, then surfaced far downstream as an unhandled `ValueError` in unrelated code (`generate_artifact_id`), caught only by a blanket `except Exception` and mis-reported as `internal_error` instead of `validation_error`. A `field_validator` alone cannot catch this class of bug because it only ever sees the already-coerced value. Any field in this codebase where a caller passing the wrong JSON type (not just an out-of-range value of the right type) must be rejected — not silently coerced — needs `Field(strict=True)` on the field itself, in addition to (not instead of) any range/enum `field_validator`.

- **Changing a shared helper's return contract requires grepping for test-local mocks of its return value, not just its production call sites (2026-07-06)**: `_search_helper.run_search_loop()` is the designated single source of truth for the search re-fetch loop, shared by `search.py` and `synthesise.py` per AGENTS.md's "fix the loop there, don't patch individual tools" guidance — but `test_tools_synthesise.py` has a test-local mock (`_mock_search_loop`) that directly replicates the function's *return shape* rather than calling through it. Changing that shape (list → tuple, to add the `fetch_exhausted` signal) silently broke 4 unrelated, previously-passing tests in that other tool's test file; `ruff` and `mypy` gave no signal, only a full test run surfaced it. When changing a shared helper's return contract in this codebase, grep test files across *all* consuming tools for mocks/fakes of that helper's return value, not just its call sites — production-code sharing conventions don't guarantee test-mock sharing.

- **A named "shared pipeline" convention doesn't guarantee the logic is actually centralized — verify by grep, don't assume (2026-07-06)**: the write path's `_section_pipeline.py` carries a "shared pipeline" comment convention implying section-handling logic lives in one place, but the section-vector-key construction (`f"{artifact_id}#{section_slug(...)}"`) was independently duplicated inline in both `write.py` and `reconcile.py` rather than routed through a shared function. This only surfaced when the H2-heading-slug-collision fix needed disambiguation logic applied in both places to stay in sync — found by explicitly grepping for the duplicated construction during review, not by trusting the shared-pipeline convention name. Before assuming a fix to one file in a "shared pipeline" area automatically covers its sibling paths, grep for the exact construction being changed across the codebase.

- **Decide up front how to mark whether a value has passed through a newly-introduced reversible encoding, or the ambiguity becomes unfixable once real data exists (2026-07-06)**: `artifact.py`'s `encode_metadata_value`/`decode_metadata_value` (added in T55 to percent-encode non-Latin titles/descriptions for S3 metadata transport) apply `urllib.parse.quote`/`unquote` unconditionally on every write/read, with no marker recording whether a given stored value was ever actually encoded. A value containing a literal `%XX`-shaped substring that was written before the scheme existed is byte-for-byte indistinguishable, on read, from one that the encoder produced from an original `%` character — `unquote` will mangle the former with no way to detect it. Arkeology-mcp has no production deployment yet, so this specific case has no real data to affect today, but the general lesson generalizes: adding a reversible encoding to a field that already has (or will ever have) real stored data needs an explicit versioning/marker decision at introduction time, because it is cheap then and effectively impossible to retrofit once any unmarked data exists.
